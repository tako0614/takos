# ドキュメントの書き方

Takos の利用者向けページは、製品内部の名前ではなく、読者が達成したいことから書き始めます。

## 基本の順序

1. このページで何ができるか
2. 事前に必要なもの
3. 最短の手順
4. 成功したときに何が見えるか
5. よくある失敗
6. 必要な人だけが読む詳細とリファレンス

README、スタートガイド、セルフホスト手順では、この順序を優先します。

## 用語

- 一般的な言葉で説明できる場合は、独自用語を作らない
- 独自用語が必要なら、最初の一回で一文に定義する
- 利用者向けページでは `App`、`実行`、`公開先` を優先する
- `Capsule`、`Interface`、`Binding` などの API 名は、API・アーキテクチャのページに寄せる
- `control plane`、`ledger`、`projection`、`materialization` のような実装語を説明なしで使わない
- “official” や “first-party” を安全性・品質の保証として使わない

用語の定義は [用語集](../reference/glossary.md) に集約します。

## 現在の挙動を書く

- 実装済み、運用者の設定次第、未対応を分ける
- 予定を現在形で書かない
- 新しい Workspace にアプリが自動追加されると書かない
- 固定のツール一覧を前提にしない
- Takos がアカウントや OpenTofu 実行を所有すると書かない
- secret を URL、Git、OpenTofu output に置く例を作らない

## 手順

- 一つの手順で一つの操作を説明する
- コマンドの前に実行場所と必要条件を書く
- コマンドの後に成功時の状態を書く
- 失敗時に確認するログ、request ID、状態を示す
- 破壊的な操作を通常のセットアップ手順へ混ぜない

## 情報設計

- `get-started`: 初めて成功するまで
- `apps`: アプリと外部接続の使い方
- `deploy`: セルフホストと運用
- `architecture`: 実装と所有者の詳細
- `reference`: API、設定、用語
- `contributing`: 開発・検証・内部 evidence

同じ説明を各ページへコピーせず、概要を一度書いて詳細ページへリンクします。
